# 账户与研究存档：成对备份、隔离恢复

本地实现，未部署；不新增网页管理员下载其他用户数据的接口。供有服务器文件权限的运维人员使用，不自动执行生产备份、停服、切换或覆盖。

## 命令

运行环境是已安装当前项目的 Python。下列路径仅为占位示例，必须替换成经核验的目录；目标父目录必须存在，目标目录必须不存在。

```bash
python -m easy_tdx.web.research_backup create --source /path/to/config --destination /path/to/backups/research-new
python -m easy_tdx.web.research_backup verify --source /path/to/backups/research-new
python -m easy_tdx.web.research_backup restore --source /path/to/backups/research-new --destination /path/to/isolated-restore
```

默认 60 秒，`--timeout` 可明确设置为大于 0 且不超过 900 秒。锁等待最长 5 秒，并受剩余时限约束；超时、容量、文件或数据问题不会悄悄跳过。单数据库工具上限 4 GiB，超过时拒绝，不截断。

三条命令成功返回 JSON `ok:true` 和退出码 0；失败退出码非零，不在输出中打印用户名、密码摘要、会话值、偏好或研究正文。路径、备份文件及输出都应只由运维人员保管。

## 备份范围与一致性

仅 `accounts.db` 和 `research_archives.db`，**不是整个配置目录或整站灾备**。策略库、后台任务、用户活动、行情缓存、运行配额、应用配置、镜像、证书和代理配置需由整站发布/灾备流程另外覆盖；不能拿仅含这两份数据库的目录直接替换全部生产配置目录。

- 账户 ID、密码摘要、角色/停用状态、授权、偏好、账户审计和登录限频记录保留。会话行仅从备份副本中清除，源库登录状态不变；恢复后需重新登录，避免旧 Cookie 因回滚重新有效。
- 备份以固定次序占用两个数据库的 SQLite 写入保留锁，两锁均取得后记录 `snapshot_at`。保留两个锁直到两份 SQLite backup 完成，因此不会分别复制两个不一致时点的账户/归属数据。使用独立读取连接调用 backup，避免在自己的写事务内备份导致等待。
- SQLite backup 包括已提交但尚未合并到主文件的 WAL，不是简单复制在线 `.db` 文件。副本转为独立 DELETE 日志模式，不依赖 WAL/SHM 伴随文件。
- 获取锁时可能暂时阻塞源库写入，请在维护窗口或低负载时使用；工具不自动进入维护模式，不假装对所有其他数据库获得原子快照。
- 正文原字节、未知历史字段、精度、备注、修订号、目录版本、回收站、永久删除墓碑和存档审计保留。不调用当前缠论算法，不重算、不补造行情，不重新绑定同名账户。

副本检查 SQLite 完整性/外键、支持的存档库版本、管理员可用性、账户字段、所有存档归属、正文摘要与容量、JSON 有限数值、状态和目录版本。只有全部完成、文件 fsync 后才写完成清单；清单记录文件哈希/大小、范围、快照/创建时间及统计。系统时钟回退时不发布完成清单。

## 验证和恢复的安全边界

- 目录独占创建，POSIX 下目录 700、文件 600；不覆盖已存在目录、不合并同名文件、不递归删除。来源与目标不能嵌套，不接受来源目录或数据库文件为符号链接。
- `verify` 检查清单版本/范围/时点、文件哈希/大小、双库内容及没有可恢复会话；拒绝缺失、篡改、含日志伴随文件或未完成的备份。
- `restore` 先验证，再复制到全新的隔离目录，复制后再核对文件摘要和归属。只在成功后写 `restore-report.json`，其中 `activated:false`。不停止服务、不切换配置、不覆盖现有生产文件。
- 不要直接用应用打开备份目录。应用初始化会运行模式检查，可能改写 SQLite 文件头，使原完成清单哈希不再匹配。先恢复到独立目录，再对该恢复目录做应用验收；备份原件保持不变。
- 失败可能留下私有的不完整目标目录，用于诊断；不会被工具视为成功备份。重试时选择另一个新目录。清理失败目录需核验目标后由运维决定，不自动清理或覆盖。
- 备份仍含密码摘要及用户研究/偏好，**并未加密**。文件权限不是加密或来源认证，SHA-256 也不是签名；必须置于可信受限存储，外传需另行加密，不能放进网页或公开源码库。
- 恢复是回到备份时点。备份以后新建的研究、账户变更、停用与删除都不在该旧快照内，可能产生回滚复活风险。上线前必须对照最新停用/删除记录并决定恢复点；工具不声称拥有跨时间删除账本，也不会自行合并或改变原档。
- `restore-report.json` 不是“已经上线”的证明。实际服务器恢复/切换、回滚保留、全配置备份、密钥管理、异地副本、留存策略和定期演练仍属于后续整站灾备/发布工作。
