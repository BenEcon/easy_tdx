# 请求资源上下文隔离修复

状态：2026-10-10 本地实现并验证，未部署。是十阶段优化中的资源保护与存档可用性修复，不代表整体目标完成。

## 原因与复现

上一轮 WebKit 出现首次目录读取 503“研究资源租约已失效”，显式刷新后正常。起初怀疑冷启动，本轮普通串行 HTTP 请求和一次浏览器请求顺序并未复现；不能仅凭冷启动时间判断原因。

实际用同一 TCP 连接一次发送上传 PUT 和目录 GET，旧代码稳定得到 **201 → 503**。诊断日志指出失效的是上个请求的上传句柄：`refs=0`、`lost=False`、`ordinary=False`、`upload=True`，不是当前用户用完了配额，也不是数据库丢失数据。

HTTP/1.1 连续请求会在前一个响应发送时调度下一个请求；该任务可能继承前一请求的 ContextVar。GET 本身没有上传 guard，因此仍读到已释放的 `_current_upload`，在同步存档操作中 retain 时失败。普通 data 依赖虽会覆盖自身上下文，但豁免配额的控制接口也不应继承上次请求的句柄。

## 修复边界

- 每个 `/api/` HTTP 请求进入安全中间件时，分别将普通研究和上传的当前句柄置空；当前请求通过原有身份和额度检查重新获取自己的租约。
- 只隔离本应用这两项状态，不清空 tracing 等第三方上下文；成功、异常、取消均用 token 恢复调用方上下文。
- 不释放调用方或上个请求的租约，不忽略工作期间真实的租约失效，不放宽并发上限、身份、大小或同源检查。
- 当前请求的子线程/后台计算仍继承并 retain 自己的租约。HTTP 等待结束后真实工作未结束，配额继续占用；已有超时/取消验收继续通过。

## 验证证据

- 新增 6 项回归：继承活跃/已释放上传句柄时目录不得借用；成功/异常/取消隔离且不影响外部 tracing 和原有工作；真实 Uvicorn H11 协议处理上传→目录→详情的 pipeline，检查原档和配额最终归零。协议测试使用内存 transport，无真实监听端口，适合 CI。
- 修复前新增的前 5 项全部失败，记录 `regression-before.log`；实际 TCP 旧版 `pipeline-before.log` 为 201/503，诊断见 `server-before.log`。初版失败测试的探针曾额外 retain 句柄，最终改为只读 ContextVar，避免失败探针本身保留资源。
- 修复后最终相关 **177 项测试通过**，覆盖资源、上传、请求/账户安全、安全审计、存档存储/API/重算和用户活动；1 条已有 Starlette 弃用警告。Ruff 检查和格式通过，严格 Mypy **298 个源文件通过**。本轮无前端源改动，不冒充全库/生产回归。
- 相同实际 TCP probe 修复后 **201 → 200**；正式本机应用 + 临时 Cookie/SQLite 的 WebKit 上传两份合成原档后，首次目录 GET **200**，无需刷新，服务端无新的 STALE_CONTEXT/503。原浏览器错误并非声称“每次冷启动必然发生”，稳定证明采用上述协议复现。
- 所有日志在 `output/resource-context-20261010/`。`source-before.tar.gz` 保存本轮开始前的资源/上传/存档路由、已有测试与台账；安全中间件的本轮新增边界可用同目录 `request-security-rollback.patch` 精确撤销。只恢复本轮改动，不能整体覆盖其他未提交工作。
